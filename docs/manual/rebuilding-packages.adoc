[[full-rebuild]]
=== Understanding when a full rebuild is necessary

Buildroot does not attempt to detect what parts of the system should
be rebuilt when the system configuration is changed through +make
menuconfig+, +make xconfig+ or one of the other configuration
tools. In some cases, Buildroot should rebuild the entire system, in
some cases, only a specific subset of packages. But detecting this in
a completely reliable manner is very difficult, and therefore the
Buildroot developers have decided to simply not attempt to do this.

Instead, it is the responsibility of the user to know when a full
rebuild is necessary. As a hint, here are a few rules of thumb that
can help you understand how to work with Buildroot:

 * When the target architecture configuration is changed, a complete
   rebuild is needed. Changing the architecture variant, the binary
   format or the floating point strategy for example has an impact on
   the entire system.

 * When the toolchain configuration is changed, a complete rebuild
   generally is needed. Changing the toolchain configuration often
   involves changing the compiler version, the type of C library or
   its configuration, or some other fundamental configuration item,
   and these changes have an impact on the entire system.

 * When an additional package is added to the configuration, a full
   rebuild is not necessarily needed. Buildroot will detect that this
   package has never been built, and will build it. However, if this
   package is a library that can optionally be used by packages that
   have already been built, Buildroot will not automatically rebuild
   those. Either you know which packages should be rebuilt, and you
   can rebuild them manually, or you should do a full rebuild. For
   example, let's suppose you have built a system with the +ctorrent+
   package, but without +openssl+. Your system works, but you realize
   you would like to have SSL support in +ctorrent+, so you enable the
   +openssl+ package in Buildroot configuration and restart the
   build. Buildroot will detect that +openssl+ should be built and
   will be build it, but it will not detect that +ctorrent+ should be
   rebuilt to benefit from +openssl+ to add OpenSSL support. You will
   either have to do a full rebuild, or rebuild +ctorrent+ itself.

 * When a package is removed from the configuration, Buildroot does
   not do anything special. It does not remove the files installed by
   this package from the target root filesystem or from the toolchain
   _sysroot_. A full rebuild is needed to get rid of this
   package. However, generally you don't necessarily need this package
   to be removed right now: you can wait for the next lunch break to
   restart the build from scratch. If you only need its files out of
   the target root filesystem, see +make target-reinstall+ below.

 * When the sub-options of a package are changed, the package is not
   automatically rebuilt. After making such changes, rebuilding only
   this package is often sufficient, unless enabling the package
   sub-option adds some features to the package that are useful for
   another package which has already been built. Again, Buildroot does
   not track when a package should be rebuilt: once a package has been
   built, it is never rebuilt unless explicitly told to do so.

 * When a change to the root filesystem skeleton is made, a full
   rebuild is needed. However, when changes to the root filesystem
   overlay, a post-build script or a post-image script are made,
   there is no need for a full rebuild: a simple +make+ invocation
   will take the changes into account.

 * When a package listed in +FOO_DEPENDENCIES+ is rebuilt or removed,
   the package +foo+ is not automatically rebuilt. For example, if a
   package +bar+ is listed in +FOO_DEPENDENCIES+ with +FOO_DEPENDENCIES
   = bar+ and the configuration of the +bar+ package is changed, the
   configuration change would not result in a rebuild of package +foo+
   automatically. In this scenario, you may need to either rebuild any
   packages in your build which reference +bar+ in their +DEPENDENCIES+,
   or perform a full rebuild to ensure any +bar+ dependent packages are
   up to date.

Generally speaking, when you're facing a build error and you're unsure
of the potential consequences of the configuration changes you've
made, do a full rebuild. If you get the same build error, then you are
sure that the error is not related to partial rebuilds of packages,
and if this error occurs with packages from the official Buildroot, do
not hesitate to report the problem! As your experience with Buildroot
progresses, you will progressively learn when a full rebuild is really
necessary, and you will save more and more time.

For reference, a full rebuild is achieved by running:

----
$ make clean all
----

When only the content of the target root filesystem needs to be
re-created, for example to get rid of the files of a package that was
removed from the configuration, a lighter alternative is:

----
$ make target-reinstall
----

It removes +output/target+ and installs all the enabled packages into
it again, without rebuilding them, then runs the usual finalization
steps (root filesystem overlays, post-build scripts) and generates the
images. The toolchain _sysroot_ (+output/staging+) is not changed, and
packages built against a removed package keep using it: in that case,
a full rebuild is still needed.

[[rebuild-changed-packages]]
==== Rebuilding the packages whose build configuration changed

.Note
This feature is experimental.

When +BR2_REBUILD_CHANGED_PACKAGES+ is enabled (in +Build options+),
Buildroot records how each package is built, in its build step. It
makes a text of:

 * the definition of all the make variables of the package
   (+FOO_VERSION+, +FOO_DEPENDENCIES+, +FOO_CONF_OPTS+, +FOO_BUILD_CMDS+,
   ...), verbatim, as written in the +.mk+ files, before expansion; also,
   defined or not, those the package infrastructures read (e.g.
   +FOO_INSTALL_INIT_SYSV+) and those its variables refer to, so that a
   variable defined only when an option is enabled is recorded too;
 * the configure and build commands of the package (+FOO_CONFIGURE_CMDS+,
   +FOO_BUILD_CMDS+ and the hooks run before and after them, including
   those of the package infrastructure), expanded, as they are run: so
   the options they get from other variables, such as the compiler
   flags, are recorded too;
 * the value of the configuration options (+BR2_+ variables) the
   variables of the package refer to, as some are read only by its
   install commands, which are not expanded (e.g. the watchdog period
   of +busybox+);
 * the SHA256 hashes of the files of the directory of the package (its
   +.mk+ file, patches, init scripts, configuration files, ...), of
   its patches from +BR2_GLOBAL_PATCH_DIR+, of the files its options
   refer to, such as a custom configuration file, and of the files its
   variables refer to under the Buildroot or a br2-external tree (e.g.
   +$(BR2_EXTERNAL_FOO_PATH)/board/foo.conf+); for such a directory
   (e.g. of patches), the names, sizes and modification times of its
   files. The files of the host system that options refer to (e.g. the
   host tools, +/usr/bin/cmake+) are left out.

Only the SHA256 hash of this text, computed with the +sha256sum+ tool
of the host, is kept, in the +.stamp_build_record+ file of the build
directory of the package
(+output/build/<package>-<version>/.stamp_build_record+), along with
the packages the package is built against (its dependencies).

At each build of the whole system (+make+, +make all+, +make world+,
+make sdk+ or +make target-reinstall+, also with other goals, but not
+make -n+), before building anything, Buildroot makes the same
text from the current definitions and patches, and compares its hash
with the recorded one. Building a single package (+make <package>+)
does not. It removes the build directory of:

 * the packages no longer enabled;
 * the packages that would be built differently: for example, after
   enabling +openssl+, +ntp+ is rebuilt, as it then depends on it and
   is configured with OpenSSL support;
 * the packages built against any of them.

The files the removed packages installed in the target directory, in
the _sysroot_ (+output/staging+), in the host directory and in the
images directory are removed too (with per-package directories, from
the final directories, made of the per-package ones). Buildroot knows
them from the list it makes of the files installed by each package,
when it is installed (+.files-list.txt+, +.files-list-staging.txt+,
+.files-list-host.txt+ and +.files-list-images.txt+ in its build
directory; the images only for the packages installing images, as this
directory is shared even with per-package directories, where packages
are built in parallel). A file also installed by a package that is not
removed is kept. The packages still enabled are then rebuilt.

The target directory is re-created instead, as with +make
target-reinstall+, when a removed package has no file list. +make
target-reinstall+ can also be used to get a target directory exactly
made of what the packages install, e.g. when a file of a removed
package was modified by a package that is not removed.

The time penalty is around a few seconds, negligible compared to the
time saved by not rebuilding from scratch.

.Tip
A package rebuilt this way is built again in a new build directory: the
old one is removed, not reused, so that the result is the same as a
clean build. To make these rebuilds fast, also enable +BR2_CCACHE+ (see
xref:ccache[]): ccache reuses the compilations whose input and options
did not change, and the build stays clean. With +BR2_PACKAGE_CACHE+ (see
xref:package-cache[]), the packages found in the cache are not built at
all, and ccache speeds up the ones that are.

+make show-stale+ lists the
packages that the next +make+ rebuilds, and those it removes, without
doing it. To see why a package is rebuilt, build it with +make V=1+:
the text is then also kept in +.stamp_build_record.verbose+, and
+make V=1 show-stale+ writes the current one in
+.stamp_build_record.verbose.new+, next to it.

+make <package>-remove+ removes a given package and the packages built
against it, and their files: the ones still enabled are rebuilt.

This does not detect everything:

 * The content of the files installed by a package does not trigger a
   rebuild: Buildroot knows which files each package installs, but not
   which files a package uses while it is built. Only the dependencies
   of a package, and the way it is built, are compared.
 * A change in the content of a file used by a package that is neither
   in its directory, nor referred to by one of its options, nor by a
   literal path under the Buildroot or a br2-external tree in its
   variables (e.g. a path made of other variables), or in a host tool,
   is not detected.
 * A package that finds an optional library in the _sysroot_ without
   depending on it is not rebuilt when the library is added or
   removed.

In these cases, +make <package>-remove+ can be used to remove a package
and the packages built against it: those still enabled are rebuilt.

Packages built before the option was enabled have no record, and are
not checked until they are rebuilt. Any change made by hand in the
build directory of a removed package is lost.

[[package-cache]]
==== Sharing the result of the builds of the packages

.Note
This feature is experimental.

When +BR2_PACKAGE_CACHE+ is enabled (in +Build options+), the result of
the build of each package is stored in a cache, in
+BR2_PACKAGE_CACHE_DIR+, shared by all the outputs of the machine.
When a package is to be built the same way as a package in the cache,
in another output or in the same one (e.g. after an option is enabled
then disabled), it is restored instead: its download, extract, patch,
configure and build steps are skipped, and its build and install steps
restore it. Its sources are only downloaded, extracted and patched:

 * for the targets that need them (+make legal-info+, +make source+,
   +make <package>-source+, +make <package>-extract+ and +make
   <package>-patch+);
 * when its hooks run outside of its steps use its build directory
   (e.g. +busybox+, whose configuration is read when the target
   directory is finalized);
 * when the hooks of its download, extract or patch steps write in the
   host, _sysroot_, target or images directory (e.g. the external
   toolchains, installed in the host directory when extracted);
 * for a package with a configuration editor (e.g. +make
   <package>-menuconfig+): its configuration is made from its sources.

Its key is computed when it is downloaded: the packages it is built
against are downloaded before it.

The package cache needs per-package directories
(+BR2_PER_PACKAGE_DIRECTORIES+): without them, a package may find, and
use, a library installed by a package it does not depend on, which its
key does not cover. It also needs +python3+ (3.7 or later) on the host.

The result of the build of a package is what it adds, changes and
removes in its host, _sysroot_ and target directories, from when it is
configured to when it is installed. Its key is the SHA256 hash of:

 * its build record (see xref:rebuild-changed-packages[]), where the
   paths of the output, host, download, Buildroot, br2-external and
   ccache directories are replaced by their names;
 * the files of Buildroot used to build all the packages: its top-level
   makefiles and +Config.in+ files, the +arch+, +system+ and +support+
   directories (except the tests), and the infrastructures of the packages
   and toolchains;
 * the host system: its architecture and distribution, the version of
   its compilers, linker, C library, Python, Perl, make and tar, and of
   cmake when the one of the host is used; with +BR2_REPRODUCIBLE+, the
   date recorded in the files (+SOURCE_DATE_EPOCH+);
 * the keys of the packages it is built against.

When a package is restored in another output, the paths of the output,
host, download, Buildroot, br2-external and ccache directories are
replaced in its text files (e.g. libtool +.la+ or pkg-config files) and symbolic links.
When the result of a package contains them in a binary file (e.g. the
RPATH of a host tool, or the toolchain wrapper with
+BR2_REPRODUCIBLE+), it is only restored where these directories are
the same. It is not restored where one of the directories its text files
contain does not exist (e.g. a br2-external tree that is not used).

Some packages are not cached, nor the packages built against them, as
the result of their build may not be known: the packages whose sources
are local (+FOO_SITE_METHOD = local+) or overridden
(+FOO_OVERRIDE_SRCDIR+), or not checked with a hash; the packages
installing or referring to images (+BINARIES_DIR+), as the packages are
installed there in parallel; the packages
rebuilt with +make <package>-rebuild+ or +make <package>-reconfigure+,
or configured with +make <package>-menuconfig+ (or another configuration
editor), as their build directory may have been modified by hand. A package is not
stored when a package it is built against was rebuilt by hand after its
key was computed.

When other packages use the build directory of a package (e.g.
+python3+: the target Python packages are built against it), that build
directory is stored with the package, without the files of Buildroot
(+.stamp_*+, +.cache_*+, +.files-list*+), and restored with it. When a
package is enabled after a package whose build directory it uses was
restored without it, the build stops, asking to remove that build
directory.

+make <package>-reinstall+ looks a restored package up again, with its
current definitions. +make <package>-rebuild+ and +make
<package>-reconfigure+ build a restored package from its sources. +make
target-reinstall+ restores the target directory of the restored
packages again.

An input of a package that its build record does not cover (see the
limits in xref:rebuild-changed-packages[], e.g. a file it uses through a
path made of other variables) is not in its key either: when it
changes, the package is restored as it was built, even after +make
<package>-dirclean+ or in a new output. To build it again, use +make
<package>-rebuild+ (the package is then neither restored nor stored any
more, until its build directory is removed), or remove its entries from
the cache (+<cache>/<package>+).

The result of each package is stored compressed with zstd when the
+python3+ of the host is 3.14 or later, else with gzip. A host with an
older +python3+ does not restore the entries compressed with zstd: it
builds these packages instead.

The cache is never cleaned up. An entry (+<cache>/<package>/<key>+) is
touched each time it is restored: the entries not used for a while can
be removed with +find+ and its +-mtime+ option.

With +BR2_PACKAGE_CACHE_VERIFY+, the packages found in the cache are
built instead of restored, and the result of their build is compared
with the cache: the differences are appended to
+package-cache-verify.txt+, in the output directory (remove it to start
over). As most packages record the time they are built, use it with
+BR2_REPRODUCIBLE+.

[[rebuild-pkg]]
=== Understanding how to rebuild packages

One of the most common questions asked by Buildroot users is how to
rebuild a given package or how to remove a package without rebuilding
everything from scratch.

Removing a package is unsupported by Buildroot without
rebuilding from scratch. This is because Buildroot doesn't keep track
of which package installs what files in the +output/staging+ and
+output/target+ directories, or which package would be compiled differently
depending on the availability of another package.

The easiest way to rebuild a single package from scratch is to remove
its build directory in +output/build+. Buildroot will then re-extract,
re-configure, re-compile and re-install this package from scratch. You
can ask buildroot to do this with the +make <package>-dirclean+ command.

On the other hand, if you only want to restart the build process of a
package from its compilation step, you can run +make <package>-rebuild+. It
will restart the compilation and installation of the package, but not from
scratch: it basically re-executes +make+ and +make install+ inside the package,
so it will only rebuild files that changed.

If you want to restart the build process of a package from its configuration
step, you can run +make <package>-reconfigure+. It will restart the
configuration, compilation and installation of the package.

While +<package>-rebuild+ implies +<package>-reinstall+ and
+<package>-reconfigure+ implies +<package>-rebuild+, these targets as well
as +<package>+ only act on the said package, and do not trigger re-creating
the root filesystem image. If re-creating the root filesystem in necessary,
one should in addition run +make+ or +make all+.

Internally, Buildroot creates so-called _stamp files_ to keep track of
which build steps have been completed for each package. They are
stored in the package build directory,
+output/build/<package>-<version>/+ and are named
+.stamp_<step-name>+. The commands detailed above simply manipulate
these stamp files to force Buildroot to restart a specific set of
steps of a package build process.

Further details about package special make targets are explained in
xref:pkg-build-steps[].
